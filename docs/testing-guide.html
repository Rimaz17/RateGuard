What RateGuard is, in one paragraph

RateGuard is a small web service that answers one question for other applications: "should I allow this request?" An application sends RateGuard the method and path of a request it received (for example GET /api/products) plus the caller's API key. RateGuard finds the caller's plan ("5 requests per 5 minutes", say), takes one token from that caller's bucket, and answers 200 (allow) or 429 (too many requests). Buckets live in Redis so several RateGuard copies share one limit. Plans, applications and keys live in PostgreSQL. You manage them through an admin API protected by an admin token.

RateGuardThe Go service (in a Docker container)http://127.0.0.1:8080
PostgreSQLDatabase: plans, applications, keys, usage127.0.0.1:5433

1.3 Start RateGuard

  1. Start Docker Desktop from the Start menu. Wait until the whale icon in the taskbar stops animating and Docker Desktop says Engine running (under a minute).
  2. In the VS Code terminal (PowerShell), make sure you are on the latest code: 
    git checkout main
git pull
  3. Create your settings file if it does not exist yet (on your PC it already does; this command only copies when the file is missing, so it is always safe): 
    if (-not (Test-Path .env)) { Copy-Item configs\.env.example .env }
    .env holds local settings, including the admin token change-me-local-only-admin-token-0000 used throughout this guide.
  4. Start from an empty database. The expected results in this guide assume nothing has been created yet. Your PC's database still holds test data from the load tests (including a default plan of 3 requests an hour), which would change the numbers you see. This command stops everything and deletes all local RateGuard data (only the data in Docker, never your code): 
    docker compose down -v
  5. Build and start everything (the first build takes a few minutes; later starts take seconds): 
    docker compose up -d --build --wait
  6. Check what is running: 
    docker compose ps -a
Expected The up command ends with lines like Container rateguard-rateguard-1 Healthy, …-postgres-1 Healthy, …-redis-1 Healthy. In docker compose ps -a, rateguard, postgres and redis are Up (healthy) and migrate is Exited (0). That is correct: migrate is a one-off job that creates the database tables and then stops.
If it fails On a brand-new database, up occasionally stops with dependency postgres failed to start, because the first boot of Postgres restarts itself once. Just run the same up command again. If it says a port is already allocated, another program uses 8080, 5433 or 6379: change RATEGUARD_HOST_PORT, POSTGRES_HOST_PORT or REDIS_HOST_PORT in .env and run up again (and use the new port in Postman).

Quick check in the browser

Open http://127.0.0.1:8080/readyz in any browser. You should see {"status":"ready","checks":{"postgres":"ok","redis":"ok"}}. RateGuard is running.

1.4 Set up Postman

a) Create an environment (stores values you reuse)

  1. In Postman's left side bar click Environments, then the + button. Name it RateGuard Local.
  2. Add these variables (type the name in the Variable column and the value in the Initial value and Current value columns, or the single Value column in newer versions). Leave the last six empty: requests fill them in for you.
    VariableValue
    baseUrlhttp://127.0.0.1:8080
    adminTokenchange-me-local-only-admin-token-0000
    clientId, apiKey, keyId, apiKey2, freeId, premiumId(leave empty)
  3. Click Save (or Ctrl+S).
  4. In the top-right corner of Postman there is a drop-down that says No environment. Choose RateGuard Local. Forgetting this is the most common mistake: every {{baseUrl}} would then be blank.

b) Create a collection (a folder for your requests)

  1. Click Collections in the left side bar, then +, and name it RateGuard Tests.
  2. For each test: click the ⋯ next to the collection, choose Add request, give it the test's name, and fill it in as described. Saved requests can be re-sent later with one click.

c) The parts of a Postman request you will use

WhereWhat to do

Reading the response (bottom half of the window)

  • Status: top right of the response area, e.g. 200 OK or 429 Too Many Requests. In this service, the status code is the answer.
  • Body tab with Pretty selected: the JSON reply.
  • Headers tab: the response headers, for example X-RateLimit-Remaining and X-Request-Id.

1.5 How to read this guide

  • Do the Part 2 tests in order. Later tests use values (keys, IDs, plans) that earlier tests create.
  • Each test has a request table (what to fill in), an Expected box (what you should see) and a line on what it proves.
  • IDs, keys and request IDs are random, so yours will differ from the examples. Things like 01a1abee-… or rg_sho_… stand for those.
  • Numbers that depend on time (reset_after, retry_after) count down while you work, so yours may be a few seconds lower.
  • Every error response has the same shape: {"error":"<message>","request_id":"<random id>"}. The guide shows only the message.
Tip If a test goes wrong and you want to start over, run docker compose down -v then docker compose up -d --build --wait, clear the six empty variables in Postman, and restart at T1.

Part 2. Manual tests in Postman

Health, security, plans, limits, keys, analytics and metrics. Allow about 45 minutes.

T1. Liveness: is the process up?

RequestGET {{baseUrl}}/healthz
AuthorizationNo Auth
Expected Status 200 OK. Body {"status":"ok"}. In the response Headers tab there is an X-Request-Id with a random 32-character value.
Proves: the service is running. Every response carries a request ID for tracing.

T2. Readiness: can it reach its databases?

RequestGET {{baseUrl}}/readyz
AuthorizationNo Auth
Expected Status 200 OK. Body {"status":"ready","checks":{"postgres":"ok","redis":"ok"}}.
Proves: readiness really checks Postgres and Redis (Part 3 shows it turning red).

T3. Admin API refuses a missing token

RequestGET {{baseUrl}}/v1/clients
AuthorizationNo Auth
Expected Status 401 Unauthorized. Body error: "a valid admin token is required". Headers include Www-Authenticate: Bearer realm="rateguard-admin".
Proves: nobody can manage applications or plans without the admin token.

T4. Admin API refuses a wrong token

RequestGET {{baseUrl}}/v1/clients
AuthorizationBearer Token, Token: wrong
Expected Status 401 Unauthorized, same error as T3. Now change the token to {{adminToken}} and send again: 200 OK with body {"clients":[]} (the database is empty).
Proves: only the exact admin token works.

T5. Register an application and get its API key

An "application" (called a client in the API) is a program that will call RateGuard. Registering it creates its first API key.
RequestPOST {{baseUrl}}/v1/clients
AuthorizationBearer Token: {{adminToken}}
Body (raw, JSON){"name": "Shop App"}
Scripts → Post-response
const r = pm.response.json();
pm.environment.set("clientId", r.client.id);
pm.environment.set("apiKey", r.api_key.key);
pm.environment.set("keyId", r.api_key.id);
Expected Status 201 Created. The body has two parts: 
{"client":{"id":"01a1abee-…","name":"Shop App","policy_id":null,"status":"active",…},
 "api_key":{"id":"01a1abee-…","prefix":"rg_sho_d3tttpsmd3rk7gsz","active":true,"revoked_at":null,
            "key":"rg_sho_d3tttpsmd3rk7gsz_<52 more letters and digits: the secret part>"}}
The key starts with rg_sho_ ("sho" from "Shop App"). Open the environment (eye icon, top right) and check that clientId, apiKey and keyId are now filled in.
Proves: registration works and the full key is returned. This is the only time RateGuard ever shows it: it stores just a SHA-256 fingerprint.

T6. With no plan at all, requests are refused

This is the main request of the whole service: "may this caller do GET /api/products?" You will send it many times. Save it as "Check".
RequestPOST {{baseUrl}}/v1/check
AuthorizationBearer Token: {{apiKey}} (the application's key, not the admin token)
Body (raw, JSON){"method": "GET", "path": "/api/products"}
Expected Status 403 Forbidden. Error: "no rate-limit policy applies to this caller".
Proves: a caller without a plan is never treated as "unlimited". RateGuard fails safe.

T7. Create the default plan "Free"

A policy is a plan: how many requests (capacity) per how many seconds (window_seconds). The default policy applies to anyone without a plan of their own.
RequestPOST {{baseUrl}}/v1/policies
AuthorizationBearer Token: {{adminToken}}
Body (raw, JSON){"name": "Free", "capacity": 5, "window_seconds": 300, "default": true}
Scripts → Post-responsepm.environment.set("freeId", pm.response.json().id);
Expected Status 201 Created. Body: 
{"id":"01a1abee-…","name":"Free","capacity":5,"window_seconds":300,
 "refill_rate":0.016666666666666666,"enabled":true,"default":true,…}
refill_rate is tokens per second: 5 ÷ 300, i.e. one token back every 60 seconds. The Headers tab shows Location: /v1/policies/<id>.
Proves: plans can be created, and the refill rate is worked out for you when you leave it out.

T8. Use up the bucket: five allowed, the sixth refused

Go back to the saved Check request from T6 and click Send six times, one after another (finish within about 50 seconds). After each click, look at the status, the body and the Headers tab.
ClickStatusBody
1200 OK{"allowed":true,"limit":5,"remaining":4,"reset_after":60}
2200 OK…"remaining":3,"reset_after":118 (about)
3200 OK…"remaining":2,"reset_after":176 (about)
4200 OK…"remaining":1,"reset_after":234 (about)
5200 OK…"remaining":0,"reset_after":292 (about)
6429 Too Many Requests{"allowed":false,"limit":5,"remaining":0,"reset_after":290,"retry_after":50} (about)

In the response Headers tab of every click: X-RateLimit-Limit: 5, X-RateLimit-Remaining equal to remaining, and X-RateLimit-Reset equal to reset_after. Click 6 also has Retry-After: 50 (about), equal to retry_after.

Expected Exactly five 200s, then 429. remaining goes 4, 3, 2, 1, 0. reset_after = seconds until the bucket is full again; retry_after = seconds until one token is back. Both are counts of seconds, not clock times. Your seconds will differ slightly depending on how fast you click.
Proves: the token bucket works and the 429 carries the standard rate-limit headers your app can copy onto its own response.

T9. Peek: ask without spending a token

RequestPOST {{baseUrl}}/v1/peek (duplicate "Check": right-click → Duplicate, then change check to peek)
Authorization / BodySame as T6
Expected Status 200 OK even though the bucket is empty. Body {"allowed":false,"limit":5,"remaining":0,"reset_after":…,"retry_after":…}. Send it again: still 200, still remaining: 0.
Proves: peek reports what a check would do without taking a token. It always answers 200; read allowed.

T10. Tokens come back over time

Wait until the retry_after from T8 has passed (at most about 60 seconds), then send Check once.
Expected 200 OK with "remaining":0: one token had refilled and you just used it. Send again straight away: 429.
Proves: the bucket refills steadily at the plan's rate (one token every 60 seconds for Free).

T11. An invalid API key is refused

RequestPOST {{baseUrl}}/v1/check, body as T6
AuthorizationBearer Token: rg_xxx_aaaaaaaaaaaaaaaa_bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
Expected 401 Unauthorized. Error: "invalid API key". Try also a random word like hello as the token: same 401.
Proves: a bad key is an error. It is never quietly treated as an anonymous caller.

T12. A caller with no key is limited by IP address

RequestPOST {{baseUrl}}/v1/check, body as T6

T13. Bad input is rejected with a clear message

Use the Check request (Bearer {{apiKey}}) and change only the body each time:

T14. Give the application its own plan

Step 1: create a "Premium" plan (100 requests a minute).

RequestPOST {{baseUrl}}/v1/policies, Bearer {{adminToken}}
Body{"name": "Premium", "capacity": 100, "window_seconds": 60}
Post-responsepm.environment.set("premiumId", pm.response.json().id);
Expected 201 Created, "capacity":100,"refill_rate":1.6666666666666667,"default":false.

Step 2: put Shop App on Premium.

RequestPUT {{baseUrl}}/v1/clients/{{clientId}}/policy, Bearer {{adminToken}}
Body{"policy_id": "{{premiumId}}"}
Expected 200 OK; the returned client now has "policy_id" equal to Premium's ID.

Step 3: send Check again.

Expected 200 OK with "limit":100 straight away. remaining will not be 99: the bucket keeps the tokens it had (none) and now refills at Premium's faster speed (1.67 a second), so you see a number that grows the longer you waited (right after T10 it is 0; a minute later it would be in the 90s).
Proves: each application can have its own plan, and a plan change applies at once without restarting anything.

T15. A stricter limit on one endpoint (login)

An endpoint rule gives one part of an API its own, separate limit inside a plan. Here: 3 login attempts per 5 minutes.

Step 1: add the rule to Premium.

RequestPOST {{baseUrl}}/v1/policies/{{premiumId}}/rules, Bearer {{adminToken}}
Body{"method": "POST", "path_pattern": "/api/login", "capacity": 3, "window_seconds": 300}
Expected 201 Created, {"id":"…","policy_id":"…","method":"POST","path_pattern":"/api/login","capacity":3,"window_seconds":300,…}. GET {{baseUrl}}/v1/policies/{{premiumId}}/rules lists it under "rules".

Step 2: duplicate Check, name it "Check login", set the body to {"method": "POST", "path": "/api/login"}, and send it four times.

Expected 200 "limit":3,"remaining":2 → 200 "remaining":1 → 200 "remaining":0 → 429 {"allowed":false,"limit":3,"remaining":0,…,"retry_after":…}.

Step 3: try to dodge the rule. Change the path to /api/login/ (extra slash) and send.

Expected Still 429, "limit":3. Paths are cleaned before matching.

Step 4: other traffic is unaffected. Change the method to "GET" (path /api/login) and send; then send the normal Check.

Expected Both 200 OK with "limit":100: the rule only covers POST /api/login, and its bucket is separate from the plan's main bucket.
Proves: endpoint rules apply, can't be dodged with path tricks, and don't use up the main allowance.

T16. Change a plan while it is in use

RequestPATCH {{baseUrl}}/v1/policies/{{premiumId}}, Bearer {{adminToken}}
Body{"capacity": 200}
Expected 200 OK, "capacity":200,"refill_rate":3.3333333333333335 (recomputed for you). Send Check right away: 200 with "limit":200.
Proves: changes reach the hot path immediately. Each copy of RateGuard caches plans, and every change is broadcast over Redis to clear those caches.

T18. Key rotation without downtime

Real systems change keys from time to time. RateGuard lets an application hold two keys at once: issue new → switch callers → revoke old.
#Do thisExpected

From now on Set the Check request's token to {{apiKey2}} and save it.

T23. Usage analytics

Part 3. Failure tests

What happens when a dependency dies. You stop a container with a command, test in Postman, then start it again. Run these after Part 2, in the VS Code terminal (PowerShell). The Check request should use {{apiKey2}}; Shop App is on Free (5 per 5 minutes) after T19.

F1. Redis goes down: decisions continue, still limited

#Do thisExpected
1docker compose stop redisContainer rateguard-redis-1 Stopped
2GET {{baseUrl}}/readyz503 {"status":"not ready","checks":{"postgres":"ok","redis":"unavailable"}}
3Send Check seven timesAll answered, none hang: 200 five times (remaining 4, 3, 2, 1, 0), then 429 twice. The first one may take a moment longer. The limit still holds without Redis
4Open {{baseUrl}}/metrics, search degraded and breakerrateguard_degraded_decisions_total{mode="local"} 7 (one per check in step 3) and rateguard_redis_breaker_state 2 (2 = open)
5docker compose logs --since 5m rateguardJSON lines with "level":"WARN", including "msg":"redis circuit breaker opened: rate-limit decisions are degraded"
6docker compose start redis, wait 10 seconds, send Check200 again, "remaining":4 (see the note below)
7Metrics again; logs againrateguard_redis_breaker_state 0; an "level":"INFO" line "redis circuit breaker closed: rate-limit decisions use redis again"
Proves: a circuit breaker notices Redis is gone and switches to a local in-memory bucket. Decisions keep coming, and the limit still applies: RateGuard never turns into "allow everything". When Redis returns, it switches back by itself.
Why remaining is 4 again The development Redis is configured not to save anything to disk (bucket state is short-lived by design), so restarting it starts every bucket full. In production you would only lose the counts of an outage, never the plans.

F2. Postgres goes down: decisions continue from the cache

#Do thisExpected
1Send Check once, then run docker compose stop postgresContainer rateguard-postgres-1 Stopped
2GET {{baseUrl}}/readyz503 {"status":"not ready","checks":{"postgres":"unavailable","redis":"ok"}}
3GET {{baseUrl}}/v1/policies (admin token)500 internal server error after a few seconds. No SQL text, no host names: just the generic message and a request ID
4Wait 15 seconds (longer than the cache's 10-second lifetime), then send Check a few timesNormal answers, 200 or 429 with "limit":5, exactly as before the outage. The key and plan come from the last copy in memory
5Open {{baseUrl}}/metrics, search result="stale"rateguard_cache_lookups_total{cache="api_key",result="stale"} is above 0: those checks were answered from the saved copy
6docker compose start postgres, wait 5 seconds, then /readyz and Check/readyz 200 ready; Check answers normally. Send a few more checks a few seconds apart: the stale count stops rising
Proves: rate limiting doesn't depend on the database. RateGuard keeps deciding from the keys and plans it already knows, readiness reports the outage, and error messages never leak internals.
Limits of this The saved copies are used for up to 15 minutes of outage (ADR 0021). An application RateGuard has never seen before has nothing saved, so its checks fail with 500 until Postgres is back, and admin changes are impossible while the database is down.

Expected A few minutes the first time (it downloads the Go image and the modules), then faster. Same list of ok lines as A1, and no WARNING: DATA RACE anywhere in the output.
